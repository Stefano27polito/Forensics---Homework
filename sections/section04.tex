\section{First Contact with the Bucket}

The purpose of this section is \emph{not} to find evidence, the sandbox bucket you are about
to create contains nothing incriminating. The purpose is to build a first-hand, concrete
understanding of what the S3 API actually gives you when you ask it for something, so that in
Sections 5--6, when you read exports that someone else produced, you know exactly what process
generated them and what it could or could not have captured.

\subsection{Creating the Test Bucket and Uploading Objects}

Run each command separately and check its output before moving to the next one:
\begin{lstlisting}
awslocal s3 mb s3://novadynamics-billing-archive
\end{lstlisting}
This creates an empty bucket. ``mb'' stands for ``make bucket''; a bucket is the top-level
container for objects, roughly analogous to a top-level folder, except that S3 buckets cannot be
nested inside one another.

\begin{lstlisting}
echo "test content" > contract_2026_0091.pdf
\end{lstlisting}
(You are creating a harmless placeholder file locally, standing in for the real contract
document, its actual content does not matter for this exercise.)

\begin{lstlisting}
awslocal s3 cp contract_2026_0091.pdf s3://novadynamics-billing-archive/
\end{lstlisting}
This uploads (``puts'') the object into the bucket,\\ under the key
\texttt{contract\_2026\_0091.pdf}.

\begin{lstlisting}
awslocal s3 ls s3://novadynamics-billing-archive/
\end{lstlisting}
This lists the bucket's contents, you should see your uploaded file, its size, and its upload
timestamp.

\subsection{Where Event Logs Come From}

Everything you have done so far in this section left no trace that you could go back and read.\\
The bucket holds the object, and the object carries its metadata, but nothing so far records \emph{that you asked for it}. That record, the event log, is a separate mechanism, and it exists only if someone turned it on beforehand.
\medskip

\noindent
This is the single most important structural fact about the evidence you will analyse in Section 5, so it is worth arriving at it by experiment rather than by assertion. In the next subsection you will configure event notifications on your sandbox bucket, then repeat operations you have
already performed, and observe the events appear. \\
The point is not the configuration itself but what it implies: an event log is a \emph{decision} taken by whoever administers the environment, before the fact, and it can be scoped narrowly, disabled, or never enabled at all.

\subsection{Configuring Event Notifications}

MinIO exposes event notifications through its own administrative client, \texttt{mc}, rather than
through the plain S3 API. Install it first:

\begin{lstlisting}
curl -L -O https://dl.min.io/client/mc/release/linux-amd64/mc
\end{lstlisting}
The \texttt{-L} flag is required: this URL currently redirects, and without it \texttt{curl}
saves the small redirect response instead of the actual binary. Check the file size before
proceeding, it should be tens of megabytes, not a few hundred bytes:
\begin{lstlisting}
ls -la mc
\end{lstlisting}
\begin{lstlisting}
chmod +x mc
\end{lstlisting}
\begin{lstlisting}
sudo mv mc /usr/local/bin/
\end{lstlisting}
\begin{lstlisting}
mc --version
\end{lstlisting}

\noindent
Register your local MinIO instance with \texttt{mc}:
\begin{lstlisting}
mc alias set local http://localhost:9000 minioadmin minioadmin
\end{lstlisting}

\noindent
Events have to be delivered somewhere. We will send them to a small HTTP listener running on the
VM, so that you can read them as they arrive. Create it in a separate terminal:

\begin{lstlisting}
cat > webhook_listener.py << 'EOF'
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get('Content-Length', 0))
        print(self.rfile.read(length).decode(), flush=True)
        self.send_response(200)
        self.end_headers()

HTTPServer(('0.0.0.0', 8888), Handler).serve_forever()
EOF
\end{lstlisting}
\begin{lstlisting}
python3 webhook_listener.py
\end{lstlisting}

\begin{warningbox}
This command will not print anything and will not return you to the prompt, that is expected.
\texttt{serve\_forever()} blocks the terminal on purpose, waiting for an actual HTTP request to
arrive. Do not interrupt it: leave this terminal exactly as it is, and move to the next step in a
separate terminal. Output will appear here only once the events start being generated in Section
4.5.
\end{warningbox}

\noindent
Leave that terminal running and return to your first one. Point MinIO at the listener and restart
it so the new target is picked up:

\begin{lstlisting}
mc admin config set local notify_webhook:1 endpoint="http://host.docker.internal:8888"
\end{lstlisting}
\begin{lstlisting}
mc admin service restart local
\end{lstlisting}

\begin{warningbox}
The hostname \texttt{host.docker.internal} is what lets the container reach the listener running
on the VM. It resolves only because of the \texttt{-\/-add-host} flag given to \texttt{docker run}
in Section 3.4. If you started the container without that flag, remove it
(\texttt{docker rm -f minio}) and start it again with the full command from Section 3.4.
\end{warningbox}

\noindent
Now subscribe the bucket to object-creation and object-access events:

\begin{lstlisting}
mc event add local/novadynamics-billing-archive arn:minio:sqs::1:webhook --event put,get,delete
\end{lstlisting}
\begin{lstlisting}
mc event ls local/novadynamics-billing-archive
\end{lstlisting}

\noindent
With notifications now active, repeat two operations you already performed in Sections 4.1 and
4.2, and watch the listener terminal as each one runs:

\begin{lstlisting}
awslocal s3 cp contract_2026_0091.pdf s3://novadynamics-billing-archive/
\end{lstlisting}
\begin{lstlisting}
awslocal s3 cp s3://novadynamics-billing-archive/contract_2026_0091.pdf ./retrieved2.pdf
\end{lstlisting}

\noindent
The upload should produce one event, \texttt{s3:ObjectCreated:Put}. \\
The download, however,produces two: \texttt{s3:ObjectAccessed:Head} followed immediately by \texttt{s3:ObjectAccessed:Get}. \\
This is not a bug in the setup: \texttt{aws s3 cp} issues a \texttt{HeadObject} call first, to check the object exists and read its size, before issuing the \texttt{GetObject} that actually retrieves it. One command you typed produced two discrete, separately timestamped events.
\medskip

\noindent
Each event carries a timestamp, the requesting identity, the source IP address, and the object key.\\
Compare its shape with the records inside \texttt{cloudtrail\_events.json}: the field names differ, because that export follows AWS CloudTrail's schema rather than MinIO's, but the information carried is the same, and it is the same class of mechanism that produced it.
